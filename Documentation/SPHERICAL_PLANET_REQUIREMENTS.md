# Spherical planet requirements

Spherical mode (`EWorldMode::SphericalPlanet`) has been reserved since the GPU generation epic. This document
collects what the docs already say about it and what the code actually does, then lists what is needed to bring
it to the level of InfinitePlane and IslandBowl. It is a requirements list, not an implementation plan. The
plan is written after the scope decisions in §2 are taken and the cubic and island reviews
([WORLD_MODES_REVIEW_PLAN.md](WORLD_MODES_REVIEW_PLAN.md)) have reported, since several requirements share work
with island fixes (the world-bounds query, mode-aware POI sampling, the save-key fingerprint).

**Sources:**

- The docs: `Features/WORLD_MODES.md` "Spherical Planet — GPU / Analytic Gap Analysis" and its five reserved
  gaps, `LOD_SYSTEM.md`, `MAP_SYSTEM.md`, `WATER_SYSTEM.md`, `CAVE_SYSTEM.md`, `SCATTER_SYSTEM.md`,
  `Research/GEOMORPH_IMPLEMENTATION_PLAN.md`, `Research/ENGINE_INTEGRATION.md`,
  `WorldClaims/Documentation/CLAIMS_ARCHITECTURE.md`.
- A code survey on 2026-10-12.

File references are relative to `Plugins/` unless noted; line numbers are as of VoxelWorlds `a85b8c6`
(on `cc706f3` and later, `VoxelChunkManager.cpp` lines after 1650 are 16 higher). Distances
are in Unreal units (1 uu = 1 cm); the default `WorldRadius` of 100,000 uu is a 1 km planet.

**Priorities:**

- **P0:** needed for a correct, walkable planet.
- **P1:** needed for parity with the other modes (the game systems work on it).
- **P2:** later or optional.

## 1. Where spherical mode stands

What exists:

- `FSphericalPlanetWorldMode` (`VoxelWorlds/Source/VoxelGeneration/{Public,Private}/SphericalPlanetWorldMode.*`).
  It provides a radial SDF, inner and outer shell radii, a radial-depth material helper and Cartesian chunk
  transforms centred on the planet.
- A CPU generator, `GenerateChunkSphericalPlanet` (`VoxelCPUNoiseGenerator.cpp:1311-1532`). It handles radial
  depth, biomes and climate sampled by 3D direction, caves and ores by radial depth, and underwater materials
  against `WaterRadius`.
- Inner-shell, outer-shell and horizon culling in `DistanceBandLODStrategy.cpp:1074-1144`, also used for unloading.
- An analytic world mode built per config by the chunk manager (`VoxelChunkManager.cpp:975-985`).
- `GetPlanetSpawnPosition` on the config, and a visual water sphere on the test actor.

What is wrong or missing:

| # | Problem | Evidence |
|---|---------|----------|
| 1 | **GPU generation has no planet support and is on by default.** Spherical falls through to the generic 3D-noise branch, which produces blobs instead of a planet. Nothing forces CPU generation for this mode. | `Shaders/Private/GenerateVoxelDensity.usf:327-346`; `WorldModeSDF.ush:190-193` (placeholder only); `VoxelChunkManager.cpp:1003-1004`; `bUseGPUGeneration` defaults to true. **Guarded 2026-10-14 (SP-B3):** planets generate on the CPU and log why. **Fixed 2026-10-16 (SP-B4, review plan §16):** the GPU generator has a planet branch, locked to the CPU by `GPUvsCPUSphericalParity`; planets follow `bUseGPUGeneration` again |
| 2 | **The terrain is mirrored across the equator.** The noise samples `FBM(Direction.xy × 10000, 0)`, so z and −z get the same height, and features stretch north to south near the equator. The 10,000 factor is hard-coded, so feature size scales with the radius. `NoiseScale` is never read. | `SphericalPlanetWorldMode.cpp:165-181`. **Fixed 2026-10-16 (SP-B1, review plan §15):** `FBM3D` at the direction's point on the datum sphere, feature size in world units |
| 3 | **Every surface turns to snow.** Height-material rules are given the distance from the centre as "height", and the default rules put snow at ≥ 4,000. | `VoxelCPUNoiseGenerator.cpp:1458`; `VoxelBiomeConfiguration.cpp:111-132`. **Fixed 2026-10-16 (SP-B2):** the rules read the altitude above the datum |
| 4 | **The analytic surface query is wrong.** `GetTerrainHeightAt(X, Y)` returns a radius, not a Z, and only for the equatorial direction (X, Y, 0). | 5 | **No water flags.** The water-fill pass is skipped for spherical, while the underground classification pass still scans world-Z columns. | `VoxelCPUNoiseGenerator.cpp:1553-1555`, `:1686-1747`. **Fixed 2026-10-16 (SP-B7 on the CPU, SP-B8):** a radial water fill and underground classification along local down |
| 6 | **The chunk candidate set is an axis-aligned box** (XY radius × a Z range capped at ±16 chunks). At the equator, world Z is horizontal, so reach along it is cut short. | `DistanceBandLODStrategy.cpp:192-211`. **Fixed 2026-10-16 (SP-C1):** each column streams its crossing of the shell |
| 7 | **The horizon cull under-buffers distant mountains.** It adds `PlanetMaxTerrainHeight` where `√(2R·Hmax + Hmax²)` is needed. | `DistanceBandLODStrategy.cpp:1074-1144`. **Fixed 2026-10-16 (SP-C2)** |
| 8 | **Config hygiene.** `BaseHeight` is hidden in the UI for spherical but still used. Nothing checks that `PlanetMaxTerrainHeight`/`Depth` cover the real amplitude (`0.5·PlanetHeightScale + BaseHeight`), so terrain past the shell is clipped by the density quick-reject. `GetPlanetSpawnPosition` ignores terrain displacement, and no spawn code calls it. **Partly fixed 2026-10-14 (SP-A5):** `BaseHeight` is shown, and the shell and water checks warn at load; the spawn clauses stay with SP-B11 and SP-F4. Since 2026-10-16 the shell check counts continentalness's extremes (Phase 1). **Spawn fixed 2026-10-17 (SP-B11, SP-F4, review plan §17):** `UVoxelChunkManager::GetPlanetSpawnPosition` stands on the terrain, and the character's spawn search goes by direction | `VoxelWorldConfiguration.h:99-191`; `VoxelWorldConfiguration.cpp:233-259` |
| 9 | **No tests, config or map.** No automation test or content asset uses SphericalPlanet. **Partly fixed 2026-10-14:** a planet config and test map exist (SP-I1) and `VoxelWorlds.Configuration.PlanetSettings` tests the config checks; the generation tests are SP-I2. **Generation, streaming and collision tests since 2026-10-16** (SP-I2, 15 tests) | `*/Tests/*`, `Content/` |
| 10 | **Every system that reads the surface assumes +Z is up**: scatter, PCG, map, navigation, POIs, dungeons, campsites, NPCs, movement, camera, world items, water, sky, clock. See Appendix A. **Movement, camera, spawn and water fixed 2026-10-17 (Phase 3, review plan §17):** gravity toward the centre, movement and camera in the gravity frame, spawn by direction, one sea definition. **Scatter, PCG, map, navigation, NPCs, world items, sky and clock fixed 2026-10-17 (Phase 4, review plan §18); POIs, conditioning, campsites, claims and dungeons fixed 2026-10-17 (Phase 5, review plan §19)** | Appendix A |

Several docs overstate this state; they are listed in §10 of the review plan.

## 2. Scope decisions

**Decided 2026-10-12: all five recommendations accepted.** Small planets first, Cartesian chunks with a
cube-sphere surface parameterisation for 2D systems, smooth meshing only, game systems in the order given, surface
play only. **SD1 and SD5 revised 2026-10-17** for Phase 6 (review plan D17 and D18, §20): planets up to
about 1,000 km, and orbit and back.

| ID | Decision | Options | Recommendation (accepted) |
|----|----------|---------|---------------------------|
| SD1 | **Planet size** | Small, 1-10 km radius (100,000-1,000,000 uu): you can walk around it, the horizon is close, float precision is ample. Large, 50-100 km and up: at the float vertex ceiling, needs double-precision SDF math, origin rebasing and an orbital LOD | **Small first.** On a 10 km planet the eye-height horizon is ~20,000 uu, half the demo view distance, so the horizon cull rather than the view distance bounds what loads. Chunk counts should be no worse than a plane's (to be measured). Large planets become a P2 track. **Revised 2026-10-17 for Phase 6** (review plan D17, §20): planets up to about 1,000 km (R 10⁸ uu), with the precision track (SP-H1, SP-H2); Earth scale stays out |
| SD2 | **Chunk topology** | Keep the Cartesian chunk grid centred on the planet, or move to cube-sphere (warped) chunks | **Keep Cartesian.** Generation, meshing, seams, collision, fades and compression are orientation-agnostic and already work there. Add a cube-sphere *surface parameterisation* only for the 2D systems (map tiles, nav grids, POI cells, water tiles, explored-tile keys), which today key on XY and merge the two hemispheres |
| SD3 | **Meshing modes on planets** | Smooth only, or smooth and cubic | **Smooth only.** Cubic voxels on a sphere form terraces everywhere except near the six points where the world axes meet the surface. With 75-100 uu blocks and a 50 uu step height, every step there is a jump, which makes cubic planets effectively unwalkable. Cubic planets would need a cube-sphere voxel grid (SD2's rejected option) |
| SD4 | **Which game systems must work on a planet** | All (POIs, dungeons, campsites, NPCs, map, nav, save, clock), or a first subset | **Terrain, character, scatter, water, map, nav, NPCs, save, clock and sky first; POIs and campsites next; dungeons last** (they need rotated stamping on an axis-aligned voxel grid) |
| SD5 | **Space and orbit** | Surface-only, or seamless space-to-surface | **Surface-only.** An orbital LOD (quadtree on a cube-sphere, or octree) and distant-planet impostors are P2. **Revised 2026-10-17 for Phase 6** (review plan D18, D19, §20): orbit and back, the planet drawn beyond the voxel window by an analytic far mesh; no other bodies and no distant-planet impostors |

The priorities below follow these decisions. Revisiting SD1 (large planets) would move SP-H1 to P0;
revisiting SD3 (cubic planets) would bring SP-D5 in.
